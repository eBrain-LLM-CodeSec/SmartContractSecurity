## 1. Methodology and what "unresolved" means here

### 1.1 Why "unresolved" = the 5 `INCONCLUSIVE` properties, not the 9 non-PASS/FAIL properties

`summary.json` records 160 in-scope verdicts: PASS=104, FAIL=47, INCONCLUSIVE=5, INSUFFICIENT_EVIDENCE=4. The run's own headline claim ("Codex resolved 155/160, 97%") arithmetically requires excluding exactly 5 properties (160 − 155 = 5), which matches the `INCONCLUSIVE` count exactly, not `INCONCLUSIVE + INSUFFICIENT_EVIDENCE` (9). This report treats that as the operative definition of "unresolved" and confirmed it against the actual harness code rather than assuming it:

- `rtf/l11_investigation_grouping/cluster_response_validation.py`'s `resolve_property_verdicts` maps Codex's own self-reported `"verdict"` field directly through a fixed table — `_DECISION_TO_CONFORMANCE = {"PASS": PASS, "FAIL": FAIL, "INCONCLUSIVE": INCONCLUSIVE, "INSUFFICIENT_EVIDENCE": INSUFFICIENT_EVIDENCE}` — for every verdict value the model itself produces. **Both `INCONCLUSIVE` and `INSUFFICIENT_EVIDENCE` are verdict categories the model chooses to emit, not harness-invented labels.**
- The harness's *only* post-hoc downgrade path converts a claimed `PASS` to `INCONCLUSIVE` (never to `INSUFFICIENT_EVIDENCE`) when `property_counterexample_is_sufficient` or `parent_obligation_check_is_sufficient` fails (reason strings `insufficient_reasoning_rigor:*`) or when the verdict string is unrecognized (`unknown_verdict:*`). `INSUFFICIENT_EVIDENCE` is never a downgrade target and is never itself downgraded — it passes straight through as a legitimate, terminal, model-chosen answer ("the codebase genuinely doesn't contain enough evidence for a confident PASS/FAIL").
- All 5 `INCONCLUSIVE` properties in `checkpoint.jsonl` carry `"reason": null` at the top level and their `raw_entries` show `"verdict": "INCONCLUSIVE"` directly — i.e. Codex itself wrote `INCONCLUSIVE` into its structured JSON response; none of the 5 shows an `insufficient_reasoning_rigor:*` or `unknown_verdict:*` reason string that would indicate a harness downgrade from a claimed PASS.

**Conclusion: the task's stated reasoning is correct and is confirmed by the code, not just the arithmetic.** No refinement was needed — `resolve_property_verdicts` treats `INSUFFICIENT_EVIDENCE` as a distinct, legitimate terminal class exactly as hypothesized. The 4 `INSUFFICIENT_EVIDENCE` properties (`req-R-notify-news::loc0`/`loc1`, `semantic__numerical__d7c0afa15d9b::loc0`, `semantic__numerical__e4d53e8877c4::loc0`) are reported below for context only and are not part of the 5-property deep-dive.

The richer per-call metadata that *would* answer several of the table's columns directly — `ArmGResult.actual_shell_commands` (a turn/tool-call proxy), `graph_tool_calls`, `graph_unresolved_events`, `input_tokens`/`output_tokens`/`cached_input_tokens`, `timed_out`, `wall_clock_s` — is computed by `run_arm_g_bundle` (`arm_g_codex.py:396-404`) and returned in-memory as `arm_g_results`, but **`live_runner._append_checkpoint` (the only thing that persists to `checkpoint.jsonl`) writes only `case_id`, `cost_usd`, `verdicts`, and `raw_entries` — `arm_g_results` is never serialized to disk anywhere in this run's artifacts.** `summary.json` (built by `launch.py`) also does not include it. This metadata was real during the run and is now unrecoverable from any artifact available to this investigation.

Where a column below cannot be filled from `checkpoint.jsonl`, `property_clusters.json`, `audit.md`, `grade_result.json`, or the source code of the harness, it is marked **"not determinable from available artifacts"** rather than inferred.

## 3. Per-property narrative

All quotations below are verbatim from `checkpoint.jsonl` (`case_id: "2025-04-forte-foundry-combined__Float128__cluster_015"`, line 15, and `"...cluster_016"`, line 19), `raw_entries.<property_id>`.

### 3.1 `semantic__numerical__4ded5b375f66::loc0` — ln(a·b) = ln(a) + ln(b)

> "Ln approximates values with a finite 15-term series, while Float128.eq at src/Float128.sol:1070 compares packed words exactly rather than applying the documented ULP tolerance. The repository does not prove the universally quantified identity." ... "A focused runtime probe could not be executed because forge is unavailable, so no concrete unequal pair was verified." ... "Exact packed equality is stronger than the documented numerical tolerance, but the available static evidence does not establish a reproducible failing pair." (confidence: `MEDIUM`)

The reasoning is coherent and internally consistent: Codex correctly identifies the structural tension (exact-word `eq` vs. an approximate Taylor-series `ln`) that makes a `FAIL` *plausible*, searched for a concrete counterexample pair (3 and 5 mentioned), but without an actual EVM/Forge execution environment to compute real 128-bit packed values it could not *confirm* a specific failing pair, and — correctly, per the ARM_G prompt's counterexample-before-PASS discipline — declined to claim `PASS` either. This is the clearest case of the four `cluster_015` properties: the blocker named is a missing capability (test execution), not a missing reasoning step.

### 3.2 `semantic__numerical__727b659c5cb4::loc0` — term-addition precision bound

> "intermediateTermAddition truncates the expansion after 15 terms and finalTermAddition performs several rounded Float128 operations. README.md:47 explicitly says precision is not guaranteed in (1.0,1.1), with relative errors above 50% possible for large mantissas." ... "The documentation withdraws a firm tolerance in the worst region, and the available tests do not establish a universal bound. No executable probe was available locally." ... "Neither compliance nor a concrete over-tolerance result can be established without a precise applicable tolerance and numerical execution." (confidence: `MEDIUM`)

This one has a second, independent driver beyond tool absence: the property as generated presupposes "the library's stated precision tolerance" exists as a single number, but the repository's own `README.md` explicitly disclaims a firm bound in part of the domain. Even with execution access, Codex would still need a tolerance to check against — this is partially a property-under-specification issue layered on top of the forge-unavailability issue.

### 3.3 `semantic__numerical__940f6f8dab83::loc0` — ln(aⁿ) = n·ln(a)

> "The implementation uses finite-series approximation and rounded packed multiplication, and no repository test proves the identity for every positive a and integer n." ... "Static inspection shows possible independent rounding paths but does not prove a concrete mismatch; the local environment lacks forge for numerical verification." ... "A universal power identity cannot be inferred from approximate ln correctness, but a reproducible counterexample was not verified." (confidence: `MEDIUM`)

Same pattern as §3.1: Codex traced specific candidate inputs (n=0, negative n, a=3/n=3) looking for a rounding-path divergence, judged one "possible" but not confirmed, and stopped short of both PASS and FAIL for lack of execution.

### 3.4 `semantic__numerical__951eafd23a04::loc0` — ln(1.001) == ln1dot001 constant

> "Unlike ln2 and ln10, ln1dot001 is never referenced by the ln algorithm. Input 1.001 is evaluated through reciprocal reduction and the finite Taylor/partition algorithm." ... "No such path exists; equality would depend on coincidental agreement after truncation. Runtime comparison could not be performed because forge is unavailable." ... "Static evidence makes exact equality doubtful but does not alone establish the final packed-word mismatch." (confidence: `MEDIUM`)

Notably, Codex's own static reasoning here leans quite strongly toward FAIL ("equality would depend on coincidental agreement" — i.e. it believes the identity probably does *not* hold) but it withheld a `FAIL` verdict specifically because it could not compute the actual packed-word result to confirm the mismatch. Contrast this with `semantic__numerical__41702464f971::loc0` and `semantic__numerical__947e9d1d4a8e::loc0` (ln(10)==ln10 and ln(2)==ln2) in the *same* cluster, both `PASS` — for those two, Codex found the special-case algebraic reduction (reciprocal branch collapsing exactly to the stored constant) was *provably exact by inspection alone*, no execution needed. The 1.001 case has no such exact algebraic shortcut, so it falls into the execution gap.

### 3.5 `semantic__semantic__3f6a3a8698b9::loc0` — ln(e) = 1

> "Ln.ln has no special case for e and evaluates it through the approximate reduction and Taylor-series implementation at src/Ln.sol:86-227. Neither the requirement nor repository defines which finite packed approximation is 'the Float128 representation of e'." ... "No canonical packed e input is specified or present, so a unique reproducible input — and therefore the exact equality check — cannot be determined." ... "Different finite decimal approximations of irrational e can legitimately feed different packed inputs. The property is under-specified without naming the required packed word." (confidence: `HIGH`)

This is categorically different from the other four. Codex does not cite tool/execution absence at all here; it identifies a genuine ambiguity in the *property itself*, generated from `README.md`'s general "signed floating-point library" framing (confirmed in `llm_cache/a6fcd6a1...json`, the semantic-generation cache entry: the raw generated statement is literally "Ln.ln(Float128 representation of e) must return the packed-float representation of 1... if e is representable in the library" at generation-time confidence `0.7`, the lowest-confidence framing already flags the "if representable" hedge). Since *e* is irrational, there is no single canonical packed-float encoding of it, so the property as stated has no unique input to evaluate — no amount of code-reading or test execution resolves that. This is why confidence here is `HIGH` rather than `MEDIUM`: Codex is highly confident *that the property cannot be evaluated as written*, as opposed to being moderately unsure whether a numeric identity holds.

## 4. Closing: why 97% and not 100%, and is this fixable?

**Why not 100%:** across 160 investigated properties, exactly 5 were left `INCONCLUSIVE`, and all 5 cluster into one narrow area — numerical correctness of `Ln.ln`'s finite Taylor-series/reciprocal-reduction logarithm approximation against exact algebraic identities (product rule, power rule, term-addition precision, one named constant) or against an ill-defined input (`e`). Every other property in the same two clusters that had a *provable-by-inspection* algebraic shortcut (ln(1)=0, ln(2)=ln2, ln(10)=ln10, ln(1.1)=ln1dot1, reflexivity/symmetry/transitivity of `eq`, bitmask-disjointness, etc.) *was* resolved to PASS or FAIL by static reasoning alone. The unresolved 5 are precisely the ones where confirming or refuting the claim requires computing an actual finite-precision numeric result and comparing it against a tolerance — something Codex, in this run, could not do because (per its own repeatedly-stated reasoning) **it had no working `forge`/Foundry test-execution environment available inside the investigation sandbox**, only static source reading via shell tools and the graph-navigation MCP server.

**Are these fixable by a different agent architecture, or are they fundamental?** The evidence supports a split answer:

- **4 of 5 (the `cluster_015` group) look architecturally fixable, not fundamental.** The blocker Codex names in each case is the same: it can reason about *what could* make the identity fail, and even proposes candidate counterexample inputs, but cannot execute Solidity/EVM code to get a concrete number. Giving the investigation agent a real, working `forge test`/`forge script` (or an equivalent EVM/Python numeric harness for the packed-float format) inside its sandbox — the same capability the *generation*-stage cache entries and the graph-MCP-server's own compile step already assume is available elsewhere in this pipeline — would very plausibly let Codex convert several of these from `INCONCLUSIVE` to a confirmed `FAIL` (Codex's own static reasoning already leans FAIL for at least `951eafd23a04`) or `PASS`. Architecturally, this is not a reasoning-capability gap; it is a tooling-availability gap in this specific run's sandbox, and the harness's own split/retry logic (`cluster_splitting.py`) has no mechanism to detect "the agent wants a tool it doesn't have" and retry with a different toolset — an explicit, complete, well-reasoned `INCONCLUSIVE` is accepted as final, not automatically retried.
- **1 of 5 (`ln(e)=1`) is closer to a fundamental limit — of the *property*, not the agent.** No agent, however capable or well-tooled, can evaluate "Ln.ln(the Float128 representation of e) must equal 1" without first being told which finite decimal truncation of the irrational e counts as "the" representation. This is a property-generation defect (visible already at generation time in `llm_cache`'s `0.7`-confidence, hedged "if e is representable" framing), not an investigation-agent shortcoming; the fix belongs upstream in the semantic-property-generation/grounding stage (require a concrete literal for any property that names an irrational constant), not in giving the investigator better tools.

Put together: the run's 97% is not evidence of 5 irreducible unknowns in the target contract's correctness. It is 4 real numerical questions whose answers this run's Codex agent was reasoning-capable of pursuing but was execution-tooling-starved to confirm, plus 1 case where the question asked was not well-formed. Neither failure mode indicates that Codex-as-investigator is near a ceiling on this class of work; both point to concrete, addressable fixes one layer away from the investigation agent itself (sandbox tooling, and upstream property generation), not to a fundamental limit of LLM-agent code auditing.

**Relevance to the custom security-agent kernel comparison:** none of Codex's 5 residual failures are attributable to context-management/execution-loop architecture (no `MAX_TURNS`, `TIMEOUT`, `CONTEXT_LIMIT`, or `MALFORMED_OUTPUT` signal in any of the 5) — they are a missing-tool gap and one ill-posed property, both orthogonal to the custom kernel's own, much larger, context-growth failure mode documented in `RTF_SECURITY_AGENT_EFFICIENCY_INVESTIGATION_20260817.md`. Codex's ~97% therefore remains the right reliability ceiling to compare the redesigned kernel against; it is not itself inflated by the kind of failure this redesign targets.
